# Diagram Delegation

거대한 Claude 생성 코드베이스를 사람이 한눈에 읽을 수 있는 날짜별 다이어그램 문서를 만드는 워크플로우다.

주 목표는 다이어그램 문서 자체다.
그 문서를 렌즈로 아키텍처의 적합성을 점검하는 리뷰(Step 3)는 원할 때만 딸려 진행하는 덤이다.

이것은 코드 작업이 아니라 문서화 워크플로우다.
Task Delegation Workflow를 거치지 않는다.
사용자가 직접 트리거하며, 각 Step은 양방향으로 진행한다.

---

## 트리거

이 워크플로우는 항상 사용자가 시작한다.
자동으로 실행되는 경로는 없다.

- 공식 트리거: `/diagram_delegation` 슬래시 커맨드.
- 자연어 트리거: "다이어그램 만들어줘", "구조 다이어그램 그려줘", "시스템 시각화 해줘", "아키텍처 다이어그램 하자" 등 같은 의도의 요청.
- `code_review.md` Stage 2가 이번 변경이 시스템/서브시스템 구조에 영향이 크다고 판단하면, 이 커맨드를 별도로 실행하도록 **권장만** 한다 (인라인 자동 실행 금지).
- 세션 복구 시, 직전 사이클이 아키텍처에 큰 영향을 줬거나 마지막 스냅샷 이후 사이클이 여러 번 쌓였으면, Claude가 이 커맨드 실행을 권장한다.

## Reference A — 아트 티어별 표현 능력과 한계

| 항목 | ASCII | .md (Mermaid) | HTML |
|---|---|---|---|
| 다이어그램 종류 | 박스-화살표, 트리, 짧은 시퀀스 | class / sequence / state / ER / C4 / flowchart | 좌측 전부 + 커스텀 |
| 레이아웃 | 100% 수동, 정렬 오류 잦음 | 자동, 수동 제어 불가 | 자동 + 수동 오버라이드 |
| 규모 한계 | 약 12 노드, 거의 planar | 약 50 노드 | 수백 노드 (pan / zoom / filter) |
| 엣지 교차 | 사실상 불가 | 엔진이 처리, 밀도 높으면 엉킴 | filter / drill-down으로 회피 |
| 그룹핑 / 중첩 | 2단계, 비좁음 | subgraph / composite state | 무제한 + 접기 |
| 시퀀스 프래그먼트 (alt/loop/par) | 매우 지저분 | 네이티브 | 네이티브 + 상호작용 |
| 색 / 시각 인코딩 | 없음 | 제한적 (classDef) | 자유 |
| 상호작용 (접기 / 필터 / 검색 / 소스 이동) | 없음 | 거의 없음 (click 링크 정도) | 전부 가능 |
| 뷰 간 연동 | 불가 | 불가 | 가능 |
| diff / PR 리뷰 | 강함 | 강함 | 약함 (blob) |
| 읽는 위치 | 소스 안, 터미널, plain diff | GitHub, VS Code, 아티팩트 | 브라우저 전용 |
| 편집 비용 | 높음 | 낮음 | 중간 |
| 코드와 동기화 유지 | 쉬움 | 쉬움 | 어려움 (JS/CSS 부패) |

절대 한계:

- ASCII는 자동 레이아웃, 밀집 그래프, 색, 상호작용이 불가능하다. 참여자 5개 이상 또는 메시지 15개 이상 시퀀스는 폭이 터진다.
- Mermaid는 정밀 레이아웃 제어, 약 60 노드 초과 그래프, 진짜 상호작용, 뷰 간 네비게이션, 커스텀 인코딩이 불가능하다.
- HTML은 diff 리뷰가 불가능하고, 인라인이나 터미널에서 읽을 수 없으며, 렌더 결과를 Claude가 눈으로 검증하기 어렵다.

## Reference B — 에스컬레이션 규칙

콘텐츠를 담을 수 있는 가장 낮은 티어에서 시작한다.
절대 한계에 부딪힐 때만 올린다.
올릴 때마다 그 이유를 문서에 한 줄로 기록한다.

- ASCII 유지 조건: 노드 12개 이하 그리고 거의 planar 그리고 프래그먼트/동시성 없음.
- 그 외에는 Mermaid로 올린다. 표준 다이어그램 타입, 약 50 노드까지.
- HTML로 올리는 조건: 약 50 노드 초과, 또는 필터/드릴다운 없이는 안 읽힘, 또는 뷰 간 연동 필요, 또는 사용자 요청.

## 표준 뷰

고정 집합이 아니라 메뉴다.
Step 1에서 이번 실행에 어떤 뷰를 포함할지 정한다.

1. 시스템 / 모듈 맵 — 계층, 빌드 타겟, 의존 방향.
2. 서브시스템 클래스 & 연관도 — 클래스, 필드/메서드, 상속 / 합성 / 연관.
3. 객체 생명주기 & 소유권 — 누가 무엇을 생성/소유/파괴하는가, 핵심 객체의 상태 머신.
4. 런타임 / 스레드 / 데이터플로우 — 스레드, producer/consumer, snapshot/queue 핸드오프.

범위에 따라 특정 뷰에서 나올 것이 거의 없을 수 있다.
그럴 때는 "해당 없음"과 그 이유를 한 줄로 남기고 넘어간다. 억지로 그리지 않는다.

---

## Step 1 — 범위와 표현 결정 (양방향)

사용자와 다음을 확정한다.

- 대상 범위 — 전체 시스템 / 이번 사이클 변경분 / 지정 서브시스템.
- 뷰 집합 — 표준 뷰 중 무엇을 포함할지.
- 뷰별 아트 티어 — Reference A + B로 제안하고 사용자가 확정.

확정된 범위에서 `{slug}`를 도출한다 (예: `전체아키텍처`, `collision서브시스템`).
새 문서 `data/docs/DiagramDelegation/diagrams/{slug}_YYYYMMDD_HHMM.md`를 열고 확정된 계획을 첫 섹션으로 쓴다.
계획을 공유하고, 피드백을 받고, 수정하고, 사용자 승인 후에만 다음으로 넘어간다.

---

## Step 2 — 다이어그램 문서 작성

범위에 든 각 뷰에 대해:

- 코드를 읽어 모델을 추출한다.
- 모델을 먼저 평문 목록으로 쓴다 (엔티티, 관계, 생명주기, 스레드). 이 목록을 다이어그램 옆에 문서에 남겨, 독자가 둘을 대조할 수 있게 한다.
- 확정된 아트 티어로 다이어그램을 렌더한다.
- 렌더 도중 절대 한계에 부딪히면 멈추고, Reference B에 따라 티어를 올리고, 이유를 기록한다.

모든 것을 하나의 날짜별 문서에 담는다.
HTML 뷰는 사이드카 파일 `{slug}_YYYYMMDD_HHMM_{view}.html`로 저장한다. 인라인 CSS/JS만, 외부 의존성 없음.

다이어그램이 완성되면 사용자에게 묻는다.

> 다이어그램을 기준으로 아키텍처 점검(Step 3)까지 진행할까요?

- 예 → Step 3.
- 아니오 → 다이어그램 문서만으로 워크플로우 종료.

---

## Step 3 — 다이어그램 기준 아키텍처 점검 (양방향, 선택)

이 Step은 덤이다.
Step 2에서 사용자가 원할 때만 진행한다.

목적: 다이어그램을 렌즈로 삼아 아키텍처가 타당한지 판정한다.
이것은 `code_review.md`의 SOLID / 라이브러리 격리 / 테스트 리뷰가 아니다.

일치성 검사:

- 다이어그램의 각 노드와 엣지를 실제 코드와 대조하고, 맞지 않는 것을 표시한다.
- `data/docs/DiagramDelegation/diagrams/`의 직전 문서와 비교하고, commit 리포트에 드러나지 않은 채 조용히 바뀐 것을 짚어낸다.

적합성 리뷰:

- 다이어그램이 드러낸 아키텍처를 평가한다: 계층 위반, 순환 의존, 소유권 모호, 잘못된 계층에 놓인 책임, 스레드 위험.
- 각 발견 사항에 CLAUDE.md의 심각도 등급을 매긴다.
- 아무것도 고치지 않는다. 수정은 새 Task Delegation 사이클로 간다.

워크스루:

- 다이어그램을 따라가는 산문형 읽기 경로를 쓴다. 사용자가 시스템을 훑을 동선을 갖도록.

공유하고, 피드백을 받고, 수정하고, 사용자 승인까지 반복한다.

---

## 산출물

하나의 날짜별 문서 `data/docs/DiagramDelegation/diagrams/{slug}_YYYYMMDD_HHMM.md`. 다음을 담는다.

- Step 1의 범위·표현 계획,
- 뷰별 모델 목록과 다이어그램,
- (Step 3를 진행한 경우) 일치성 노트, 심각도 등급이 매겨진 적합성 발견 사항, 산문형 워크스루.

영구 보관.
archive하지 않고, 덮어쓰지 않는다.
실행할 때마다 새 날짜별 파일이 생기므로, `data/docs/DiagramDelegation/diagrams/`는 시계열로 누적되어 조용한 아키텍처 드리프트를 diff로 드러낸다.

## code_review.md Stage 2와의 관계

Stage 2는 리뷰된 코드만 대상으로 하는 작고 사이클 종속적인 class/sequence 스케치용으로 그대로 남는다.
Stage 2는 이 커맨드를 자동으로 실행하지 않는다.
리뷰 대상 변경이 시스템 또는 서브시스템 구조에 영향이 크다고 판단되면, Stage 2는 그 사실과 함께 `/diagram_delegation`을 별도로 실행하도록 한 줄로 권장하고 끝낸다.
